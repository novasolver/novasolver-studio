## High — CG can falsely report convergence

**What goes wrong:** This deterministic positive-definite system reproduces the problem:

```python
rng = np.random.default_rng(10)
Q = np.linalg.qr(rng.normal(size=(3, 3)))[0]
A = sp.csr_matrix(Q @ np.diag([1e-15, 1e-4, 1.0]) @ Q.T)
b = rng.normal(size=3)
x = fem_tet10._amg_cg(A, b)
```

The new PCG routine reports a relative residual of `1.01e-9`, but recomputing `||b - A @ x|| / ||b||` gives `0.02064`. `_amg_cg` accepts that solution despite its `1e-6` acceptance limit. The v0.7.5 implementation rejects this input.

**Why:** `_pcg_best` measures only the recursively updated residual, `r -= alpha * Ap`. Round-off can separate that vector from the actual residual. It then selects and accepts `best_x` without checking `b - A @ best_x`. The previous library routine periodically recomputed the residual. This affects structural, scalar, buckling, and nonlinear callers.

**Suggested fix:** Periodically recompute the actual residual, and always verify the returned iterate against the original system before accepting it. If that check fails, continue or trigger the existing retry/fallback.

## Medium — Midside normalization is no longer safe to repeat

**What goes wrong:** I generated a unit-sphere tet10 mesh with `MeshSizeMax=0.6`, then scaled its coordinates by `(1, 0.01, 0.01)`. The correctly ordered mesh has zero folded elements. `mass_matrix(nodes, raw_tets, rho)` succeeds, but `solve_modal` fails with:

```text
ValueError: midside node matching failed (curved or non-conforming mesh)
```

**Why:** The first `canonical_tets` call correctly invokes the new Gmsh-order fallback. `solve_modal` then passes those canonical elements to `mass_matrix`, which calls `canonical_tets` again. When geometry remains ambiguous, the fallback assumes Gmsh ordering again and swaps columns 8 and 9 a second time. The resulting connectivity fails the consistency check.

**Suggested fix:** Make the input ordering explicit and normalize once. Separate conversion from Gmsh ordering from operations on canonical connectivity, or pass an explicit ordering flag through callers such as `mass_matrix`.

## Medium — STL retries do not refine the failing surface

**What goes wrong:** For an STL volume job with `surf_cap=0.002` and `surf_factor=1.0`, instrumenting the retry path showed that every attempt passes exactly `(target=0.002, factor=1.0)` to `import_stl`, including attempts advertised as size factors `0.5` and `0.25`.

A failure caused by the coarse surface therefore gets the same surface again instead of the intended finer one.

**Why:** `_size_factor` scales `h` later in `mesh_job`. STL surface remeshing happens earlier and uses only `surf_cap` and `surf_factor`. Those discrete surface triangles are retained during volume generation, so changing the surface mesher does not repair this omission.

**Suggested fix:** Apply the retry factor to STL surface remeshing as well, preferably through `surf_factor` so it also scales the thickness-limited target. Argument propagation was reproduced; recovery on an actual failing STL was not run.
