## 1. Medium — Memory estimate incorrectly blocks feasible solves

**What goes wrong:** A 100 × 20 × 20 mm block with 579 nodes and 254 quadratic tetrahedra, one clamped end, and a −1 MPa traction on the opposite end is rejected when available commit is 500 MB. The error claims approximately 600 MB is required.

An in-memory reproduction mocked `committable_bytes()` to return 500 MB. Bypassing only the guard allowed the same model to solve successfully, with:

- Whole-process peak committed memory: **199.6 MB**
- Force imbalance: **1.17 × 10⁻¹²**

Thus a feasible simulation fails before assembly. Because the estimate has a 600 MB minimum, following the error’s advice to coarsen the mesh cannot resolve this condition.

**Why:** `MEM_BASE + MEM_PER_NODE[kind] * n_nodes` represents an estimated **whole-worker peak**, but `committable_bytes()` returns **additional memory currently available**. Existing process allocations are effectively counted twice. The fixed 600 MB allowance also ignores the much smaller assembly allocations of small meshes. This guard affects structural, thermal, and electric solves.

**Suggested fix:** Estimate additional peak allocation from the current solver state, accounting for actual element/chunk sizes and solver branch. Avoid using the whole-worker calibration as an unconditional rejection threshold. Add a regression covering a small feasible model with less than 600 MB available.
