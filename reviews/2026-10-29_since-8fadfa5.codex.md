## 1. High — Contact kinematics remain fixed during large deformation

**What goes wrong:** Rotate a circular shaft of radius 20 mm by 0.1 rad inside a matching circular bore. The surfaces remain geometrically touching, but the contact equations calculate approximately **0.0999 mm opening**. Contact pressure can consequently disappear incorrectly.

**Why:** `Constraints.B` is constructed once from reference normals and original master/slave node pairs. `equations()` then uses `B @ u` throughout the large-deformation solve. It never updates normals or projects sliding nodes onto the current opposing surface. The solver can converge against these incorrect constraints without warning.

**Suggested fix:** Update contact projections, normals, force directions, and their tangents using current geometry. Until implemented, explicitly restrict this formulation to small sliding and small rotations.

## 2. High — Modal analysis drops new support roles

**What goes wrong:** Keep a cantilever’s fixed root, change its opposite face to `displacement` with all components zero, then select modal analysis. The extra support contributes **zero constrained DOFs**. An in-memory mesh reproduction returned approximately **890 Hz**, versus **10,081 Hz** with the requested second support applied.

**Why:** The modal branch runs before the incremental branch that handles displacement and spring roles. `run_modal()` supplies only fixed faces and `symmetry_rollers()` to the eigenproblem; neither handles these new roles. With an existing fixed root, no free-free warning exposes the omission. CalculiX also returns from its modal compiler branch before adding prescribed displacements.

**Suggested fix:** Apply constrained displacement components to modal DOFs and add spring stiffness to the eigenproblem. Reject unsupported combinations explicitly rather than ignoring them.

## 3. High — Spring unit switching changes the model

**What goes wrong:** Enter **100,000 N/m**, then select **N/mm**. The UI commits **100,000 N/mm**, equivalent to **100,000,000 N/m**, instead of converting to **100 N/mm**.

**Why:** The backend now advertises `N/m` and `N/mm`, but `frontend/src/lib/units.ts` contains neither conversion factor. `convert()` returns `null`, and `NumberInput` preserves the number while changing its unit. A Node reproduction confirmed this path.

**Suggested fix:** Add both units under one stiffness dimension with factors `1` and `1000`. Prevent unit changes from committing when conversion is unavailable.

## 4. High — Uniform body temperatures depend on input order

**What goes wrong:** For two bonded bodies sharing mesh nodes, request uniform temperatures `b1=20°C` and `b2=100°C`. Shared interface nodes become **100°C**. Reverse the dictionary order without changing either temperature, and they become **20°C**. Adjacent elements receive different thermal strains and stresses.

**Why:** `temperatures()` assigns each body’s temperature into one global nodal array. Bonded bodies share interface node indices, so the last assignment wins. This also introduces temperature gradients into bodies requested to have uniform temperatures.

**Suggested fix:** Represent prescribed body temperatures per element or integration point. Alternatively, reject incompatible uniform temperatures on shared nodes and require an explicitly defined temperature field.

## 5. Medium — Preset changes retain the previous material law

**What goes wrong:** Create `rubber-tension`, then set `materials.solid.preset="steel"`. `solid_props()` still returns `model="neo-hookean"`. Likewise, changing `plastic-bar` to aluminium retains `model="elastoplastic"` and its previous `H=2.05e9`.

**Why:** Preset selection copies the new preset’s keys into the existing material dictionary. Ordinary metal presets lack `model` and `H`, so the previous values survive and remain active in the solver.

**Suggested fix:** Replace the material property dictionary when selecting a preset, with explicit model defaults. If constitutive overrides should persist, make that retention explicit in the UI and update contract.

## 6. Medium — CalculiX collapse verification crashes after solving

**What goes wrong:** Run `plastic-beam-collapse` with CalculiX using a reduced load that completes successfully. Postprocessing reaches `nonlinear_reference()` and raises **`KeyError('curve')`**, losing an otherwise usable result.

**Why:** `run_calculix()` builds a local `curve`, but passes `response` containing only displacement, stress, von Mises stress, and optional interfaces into verification. The collapse reference unconditionally reads `r['curve'][-1]`.

**Suggested fix:** Pass the parsed curve and required snapshots into the reference response. Handle unavailable history explicitly.

**Validation:** Reproduced the helper failure with the response shape constructed by `run_calculix()`; an end-to-end CalculiX run is still needed.

## 7. Medium — Load paths bypass history memory budgeting

**What goes wrong:** With `steps=2` and `path=[5]`, the memory guard budgets **two snapshots**, while an in-memory solve saves **ten**. The update API also accepts `path=[1e100]`, which can keep accumulating snapshots until memory exhaustion.

**Why:** The estimate uses `steps * len(path)`, while execution advances by increments bounded independently of each target’s distance. Every converged increment remains in memory, and no total-step or history-memory limit is enforced.

**Suggested fix:** Account for total path travel and adaptive subdivision when estimating history storage. Enforce a runtime snapshot or memory budget and return an actionable error before exhaustion.

## 8. Low — Zero-only paths crash with an uninitialized variable

**What goes wrong:** Submit `physics.nonlinear.path=[0]` for an otherwise valid displacement-driven case. The solver raises **`UnboundLocalError`** instead of returning a zero-load result or a validation error.

**Why:** The schedule skips targets equal to the initial fraction. No Newton loop executes, so `residual_history` is never initialized before the `last is None` error branch references it.

**Suggested fix:** Initialize history before processing the schedule and either return the initial state or reject schedules containing no effective increment.
