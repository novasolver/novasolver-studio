### 1. High — GCI normalization can falsely verify a result

**What goes wrong:** With coarse/normal/fine values `[100, 1, 0.5]` and mesh spacings `[1, 0.5, 0.25]`, `gci()` returns **0.0417%**, `asymptotic=True`. If the three solves converge and the meshes refine, the study passes and can become the verification reference. The final change equals **100% of the fine result**.

**Why:** At `run_worker.py:366`, relative error is divided by the largest value across all meshes. Here, the coarse result reduces the reported error by 200 times. Using the fine value with the same calculated order and safety factor gives **8.33%**, which fails the 5% limit.

**Suggested fix:** Normalize relative GCI against the fine result. Handle near-zero results through an explicit absolute-error tolerance; do not let a large coarse result dilute the error. Add regression cases for `[100, 1, 0.5]` and `[100, 1, 0]`.

### 2. High — Conjugate convergence checks only the last region’s enthalpy residual

**What goes wrong:** A fixed-temperature conjugate case reaches its iteration limit with final fluid enthalpy residual `0.2`, followed by solid enthalpy residual `1e-6`. With a finite outlet temperature and no imposed heat flux, the code returns `converged=True`. This was reproduced using the actual convergence assignments and a synthetic solver log.

**Why:** The regex collects `h` residuals from every region, then `resid[-1]` selects only the last solve. Momentum, pressure, other regions, and coupling convergence do not participate in this branch.

**Suggested fix:** Track residuals by iteration, region, and equation. Require all relevant final residuals to satisfy their limits, and reject iteration-limit termination unless convergence criteria were met. Report which criterion failed.

### 3. High — Autosave still mixes edits between cases while a request is pending

**What goes wrong:** Reproduced against the transpiled store:

1. Case A starts saving `boundaries.x1.force=100`.
2. While that request is pending, edit A’s force to `200`.
3. Open case B and change its mesh size to `fine`.

The resulting second request targets **B** with both:

```json
{"boundaries.x1.force":200,"mesh.size":"fine"}
```

A loses its second edit, and B silently receives A’s load.

**Why:** `change()` calls `void flush()` before adding B’s edit, but `flush()` awaits `inFlight` before detaching `pending`. During that await, B’s edit enters the same object and replaces `pendingCase`.

**Suggested fix:** Store pending edits separately for each case. Detach each batch and its case ID synchronously before awaiting anything, then serialize those immutable batches.

### 4. Medium — Curved-element membership is tested using straight corners

**What goes wrong:** Consider a tetrahedron with unit-axis corners and its edge between `(1,0,0)` and `(0,1,0)` bowed inward to midpoint `(0.45,0.45,0)`. For point `(0.45,0.45,0.05)`, the probe reports `inside=True`, although quadratic inversion produces barycentric coordinates:

```text
[-0.05, 0.5, 0.5, 0.05]
```

The point lies outside the curved element, so the returned value is extrapolated without warning.

**Why:** `locate()` accepts the straight tetrahedron first. The new quadratic inversion changes interpolation weights but never rechecks membership. Conversely, points inside outward-curved portions can be rejected before inversion.

**Suggested fix:** Perform quadratic inversion while evaluating candidate elements. Accept a candidate only after inversion converges and its coordinates satisfy the element’s membership limits.

### 5. Medium — Midside averaging is not exact on curved faces

**What goes wrong:** For a planar tri6 with corners `(0,0)`, `(1,0)`, `(0,1)` and midside nodes `(0.5,0)`, `(0.6,0.6)`, `(0,0.5)`, a temperature field `T=x` gives:

- Reported mean: **0.366667**
- Exact area-weighted mean: **0.376842**

The actual `probe()` path reproduced the reported value.

**Why:** Corner shape functions integrate to zero only when the surface mapping has constant Jacobian. Curved CAD elements have a varying surface Jacobian. The new midside averaging still weights everything using straight corner-triangle areas.

**Suggested fix:** Integrate the field and surface Jacobian using tri6 quadrature. Use the same geometry integration for face area, centroid, and velocity-derived flux.

### 6. Medium — A revision-fetch failure disables all later autosaves

**What goes wrong:** Queue an edit for A, switch to B, then make `getCase(A)` fail—for example, because another client deleted A. That flush rejects. Subsequent edits to B also reject before issuing any PATCH, and `saving` remains true. This was reproduced against the transpiled store.

**Why:** The revision lookup at line 599 is outside `try`. Its rejection escapes `run()`, leaving `inFlight` pointing to a rejected promise. Every future `flush()` immediately fails while awaiting that promise.

**Suggested fix:** Move revision acquisition inside the error handler and clear `inFlight` in `finally`. Ensure one failed batch cannot poison the queue for other cases.

### 7. Medium — Source-checkout MCP configuration omits `PYTHONPATH`

**What goes wrong:** Start Studio using the documented developer setup, then copy the AI panel’s configuration into an MCP client launched independently. It runs:

```text
<venv-python> -m novastudio mcp
```

and fails with `No module named novastudio` when its working directory is outside `backend`. With `PYTHONPATH` absent, module discovery in this checkout returned `None`.

**Why:** `environment_check()` returns only `command` and `args`. The documented setup relies on `PYTHONPATH=<studio>/backend`; the MCP client does not inherit the serving process’s environment. `AiPanel` also preserves only those two configuration fields.

**Suggested fix:** Include the required source-checkout environment in `mcp_command`, and preserve it when generating the snippet. Include the active workspace override so the MCP process opens the same cases as the UI.

### 8. Low — New convergence quantities display untranslated keys

**What goes wrong:** Completed channel and conjugate studies display `qty.study.umax_outlet` and `qty.study.t_solid_rise` as quantity labels in the UI and MCP summaries.

**Why:** `primary_quantity()` introduces those identifiers, but neither key exists in the English, Japanese, or Chinese backend dictionaries. `_conv_view()` constructs the missing keys, and translation falls back to the literal key.

**Suggested fix:** Add both quantity labels to all three backend dictionaries.
